# RAG Knowledge QA

> 设备手册知识库问答系统。把路由器、打印机、笔记本的 PDF 用户手册解析入库，
> 用户用中文自然语言提问，系统经多路混合检索与交叉编码器精排后，
> 基于手册原文作答，并附上相关的接线图、面板图。

## 这个项目解决什么问题

设备手册是 RAG 场景里最难啃的一类文档：几百页、大量表格与示意图、
章节层级混乱、关键信息常常只存在于图片里。把 PDF 粗暴地按固定长度切块
丢进向量库，召回质量会差到不可用。

| 真实场景的难点 | 本项目的应对 |
| --- | --- |
| PDF 版面复杂，表格与多栏排版直接抽文本会错乱 | MinerU 做版面解析，还原成结构化 Markdown |
| 按固定长度切块会把一句话、一张表从中间劈开 | 按 Markdown 标题层级切分，超长章节再按句末边界滑窗二次切分 |
| 关键信息在图里，纯文本检索完全看不见 | 多模态模型结合上下文为每张图生成描述，随段落一起向量化 |
| 型号、错误码（`KFR-35GW`、`E-05`）语义检索命中率低 | BGE-M3 稠密 + 稀疏双向量混合检索，稀疏向量专治字面匹配 |
| 用户的问法和手册的措辞对不上 | HyDE：先让模型写一段假设性答案，再拿它去检索 |
| 多份手册里的同名章节互相干扰 | 先识别用户问的是哪台设备，再用标量过滤把范围锁到一份手册 |
| 向量检索只能判断「是否同一话题」 | 交叉编码器精排，判断「是否真的回答了这个问题」 |
| 知识库没有答案时模型会编 | 精排结果为空时直接返回固定话术，根本不调用模型 |

## 三个核心设计决策

### 一、稠密与稀疏双向量，而非只用稠密

稠密向量擅长语义匹配：用户问「机器卡纸了怎么办」，能召回标题写着
「清除卡住的介质」的段落——字面零重合，语义高度相关。

但设备手册里充斥着 `KFR-35GW`、`E-05` 这类型号和错误码。这些符号串本身
没有语义，稠密向量对它们的区分度极差，而稀疏向量（本质是可学习的 BM25）
能精确命中。

BGE-M3 的价值正在于**一次前向传播同时产出两种向量**，省掉了维护两套模型、
跑两次编码的开销。检索时用 `WeightedRanker` 按 0.6 / 0.4 加权融合，
融合前先做分数归一化——稠密走 COSINE（值域 −1~1）、稀疏走 IP（值域无上界），
不归一化的话稀疏分数会直接淹没稠密分数，权重形同虚设。

### 二、HyDE：用假设性答案去检索，而不是用问题

向量检索本质是比较两段文本的相似度，但**问题和答案在文本形态上差异很大**。
用户问「打印出来有横条纹怎么办」，手册里对应的段落写的是「若打印结果出现
规律性横向条纹，请执行打印头清洗程序」。问句 vs 陈述句、口语 vs 术语，
直接比相似度并不高。

HyDE 先让模型凭常识写一段假想的标准答案——它是陈述句、带专业术语的，
和手册段落形态同构，向量距离自然更近。**即使模型编造的细节是错的也不要紧**：
它只用于检索，最终答案仍然完全基于真实检索到的手册内容生成。

代价是多一次 LLM 调用。所以它与常规检索**并行**执行，两路耗时重叠，
端到端只多出一次模型调用的时间。

### 三、RRF 融合 + 交叉编码器精排

两路召回的分数**不可比**——一路查的是问题、一路查的是范文，文本长度和
语义密度都不同，强行加权求和等于在比较两把刻度不同的尺子。
RRF（Reciprocal Rank Fusion）只看名次不看分数，对分数分布免疫。
常数 `k=60` 压平了头部差距，让融合更看重「在多路中都靠前」而非
「在某一路里排第一」。

融合之后还要精排，因为前面的向量检索是**双塔模型**：问题和切片各自独立编码，
从头到尾没有交互，模型无法判断「这段话是否真的回答了这个问题」，
只能判断「它们大体上是不是一个话题」。

交叉编码器把问题和切片拼成一条输入一起过模型、逐层做注意力交互，判别精度
高得多，但无法预计算——每个候选都要单独推理。所以标准做法是两段式：
**双塔负责从海量数据里快速捞出几十条候选（保召回），交叉编码器负责在这
几十条里挑出真正对题的几条（保精度）**。

## 技术栈

| 分层 | 选型 |
| --- | --- |
| 流程编排 | LangGraph，导入与查询两条独立的 `StateGraph` |
| 版面解析 | MinerU（PDF → 结构化 Markdown） |
| Embedding | BGE-M3，一次编码产出稠密 + 稀疏双向量 |
| 重排序 | BGE-Reranker-Large 交叉编码器 |
| 向量库 | Milvus，`WeightedRanker` 混合检索 + 标量过滤 |
| 对象存储 | MinIO，图片托管并生成公网 URL |
| 大模型 | 通义千问（DashScope），含视觉模型用于图片理解 |
| 会话存储 | MongoDB |
| 图谱（预留） | Neo4j |

## 快速开始

### 1. 准备依赖服务

```bash
docker compose up -d
```

### 2. 下载本地模型

```bash
python -m app.tool.download_bgem3       # BGE-M3 向量模型
python -m app.tool.download_reranker    # BGE-Reranker 重排模型
```

### 3. 配置环境变量

```bash
cp .env.example .env
```

关键配置项：

```ini
OPENAI_API_KEY=your_api_key_here
OPENAI_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_DEFAULT_MODEL=qwen-flash
VL_MODEL=qwen3-vl-flash

BGE_M3_PATH=/path/to/your/local/resource
# 有 NVIDIA 显卡填 cuda:0 并把 BGE_FP16 设为 1；
# 纯 CPU 环境必须填 cpu 且关闭 FP16，否则会抛
# "Torch not compiled with CUDA enabled"
BGE_DEVICE=cpu
BGE_FP16=0

MILVUS_URL=http://127.0.0.1:19530
CHUNKS_COLLECTION=kb_chunks

MINIO_ENDPOINT=localhost:9000
MINIO_ACCESS_KEY=your_access_id_here
MINIO_SECRET_KEY=your_secret_here

MINERU_API_TOKEN=your_token_here
```

> 仓库内不含任何真实密钥，全部凭据经环境变量注入，`.env` 由 `.gitignore` 拦截。
> 语料目录 `doc/`（约 700MB 的 PDF）同样不入版本库。

### 4. 导入文档

```bash
python -m app.import_process.agent.main_graph
```

### 5. 提问

```bash
python -m app.query_process.agent.main_graph
```

或在代码中调用：

```python
from app.query_process.agent.main_graph import answer_question

result = answer_question("MateBook B3-410 怎么进入 BIOS")
print(result["answer"])
print(result["image_urls"])
```

## 工程实践

- **导入与查询链路分离**：两条链路各有独立的 `StateGraph` 与状态定义。两者关心的数据几乎没有交集，硬塞进同一个状态字典会让每个节点都要面对一堆无关字段。
- **入库幂等**：按 `item_name` 先删后插。同一份手册改几个字重新导入，若直接插入会新旧并存，检索时同一段内容占掉多个名额，把本该召回的其他片段挤出去——这类问题表现为「答案看着没错就是不全」，极难排查。
- **向量维度不写死**：建集合时从实际生成的向量读取维度，避免配置项写错导致建表与写入对不上。
- **降级而非中断**：图片处理、主体识别、HyDE 检索、精排任一环节失败都只降级不中断——图片是增强项，主体识别失败可退化为文件名，HyDE 失败还有常规检索兜底，精排失败可退回 RRF 排序。
- **提示词与代码分离**：全部提示词存放于 `prompts/`，调整措辞无需改代码、无需重启。
- **并行分支返回局部状态**：两路检索节点只返回自己负责的字段而非完整状态——LangGraph 会合并各分支返回值，若都返回完整状态等于对每个字段并发写入，没配 reducer 的字段会直接抛 `InvalidUpdateError`。

## 评测结果

项目内置 25 道黄金评测集（`evaluation/golden_set.yaml`），按能力维度分 7 层，
基于知识库中实际存在的 11 份设备手册、1143 条切片编写，每道题的答案都逐条
对照过库中原文。

评分**分两层统计**：检索命中率与答案关键事实覆盖率分别记录。
一道题答错，可能是检索压根没找到对的片段，也可能是找到了但模型没用好——
前者要调切分与检索策略，后者要调提示词，混进一个总分里就看不出该改哪儿。

```bash
python -m app.scripts.run_evaluation -c evaluation/golden_set.yaml
```

| 指标 | 数值 |
| --- | --- |
| 总体准确率 | **96.0%**（24 / 25） |
| 检索命中率 | **92.9%** |
| 关键事实覆盖率 | **97.5%** |

### CPU 与 GPU 推理对比

同一套评测集、同一份代码，仅切换 BGE-M3 与重排模型的推理设备：

| 指标 | CPU (FP32) | GPU (FP16, RTX 4050) | 变化 |
| --- | --- | --- | --- |
| 总体准确率 | 96.0% | **96.0%** | 持平 |
| 检索命中率 | 92.9% | **92.9%** | 持平 |
| 关键事实覆盖率 | 97.5% | **97.5%** | 持平 |
| 端到端延迟 P50 | 50.7 s | **4.5 s** | ↓ 91.1% |
| 端到端延迟 P95 | 55.3 s | **12.1 s** | ↓ 78.2% |

准确率四项指标完全一致，说明 FP16 半精度并未损失检索质量；
显存占用 1.07 GB / 6.0 GB，余量充足。

**但切到 GPU 后首次评测只得 28%。** 排查过程值得记录：检索召回 20 条正常、
精排保留 5 条正常、送进模型的上下文里 4/5 条含正确答案，单独调用模型也答得对——
唯一的变量是并发。降到单并发后立刻恢复正常，日志里一条被忽略的
`精排失败：expected scalar type` 指向了真正的原因，详见下一节第 6 条。

**L2 组是这套评测集设计时最看重的一组。** 知识库里七台 H3C 路由器几乎都有
「登录 Web 设置页面」「恢复出厂设置」「缺省密码」等同名章节，L2 刻意用不指名
设备的提问去检验系统会不会张冠李戴——答案必须交代清楚出自哪台设备。

### 评测暴露并修复的六个缺陷

准确率的演进过程本身说明了问题所在：

| 轮次 | 总体准确率 | 变化点 |
| --- | --- | --- |
| 第 1 轮 | 20.0% | 基线（含线程竞态） |
| 第 2 轮 | 84.0% | 修复模型单例的线程安全 |
| 第 3 轮 | 84.0% | 修拒答判定，但提示词约束改过了头 |
| 第 4 轮 | **96.0%** | 平衡提示词 + 修正判定顺序 |

**1. 商品名规范化缺失** —— 检索静默返回空集

命令生成节点识别出的是「Aolynk CB304n 网桥」这类口语写法，而入库时经主体识别
规范化后存的是「AolynkCB304nCable网桥」。Milvus 标量过滤是精确字符串匹配，
两者对不上就过滤掉全部结果——**日志里没有任何报错**，用户只看到「知识库中没有
相关内容」，明明有答案却答不出来。

修复方式是启用库中本就存在的 `kb_item_names` 集合（每份文档一条带向量的商品名
记录），用向量检索完成口语名到规范名的映射。另外补了一层兜底：带过滤却召回为空
时自动去掉过滤重试，避免一个拼写问题让整个系统哑掉。

**2. 归一化阈值过低** —— 不存在的设备被硬匹配

阈值不是拍脑袋定的，是量出来的：

```
库中真实设备 Top1 相似度   0.8021 ~ 0.9955
库中不存在的设备           0.4459 ~ 0.5990
```

中间有 0.20 的空隙，取 **0.70**，两侧各留约 0.10 余量。阈值定低了，问「小米
路由器」会被归一化到 H3C 设备上，系统于是拿 H3C 的配置步骤去回答一台库里根本
没有的设备——这类张冠李戴比直接答不出来危险得多。

**3. 模型单例的线程竞态** —— 只在并发下出现

```python
# 修复前：embedding_utils 与 reranker_utils 都是无锁单例
if _bge_m3_ef is not None:
    return _bge_m3_ef
# ← 两个线程同时判空、同时开始加载模型
_bge_m3_ef = BGEM3EmbeddingFunction(...)
```

BGE-M3 使用 `meta` 设备做延迟初始化，一个线程会读到另一个线程尚未完成
`to(device)` 的半成品，抛出 `Cannot copy out of meta tensor`。
整轮评测出现 67 次向量生成失败、49 次检索失败，准确率从 100% 崩到 20%。

**这个缺陷在单线程下完全复现不了**：单并发时 L1 组 6/6 全过、单题耗时 17~51 秒；
并发 2 时几乎全崩、单题耗时骤降到 1.7 秒。延迟大幅下降本身就是线索——那不是
变快了，是全部快速失败。任何只做单请求验证的测试都会放过它，而线上只要有两个
用户同时提问就会触发。

修复用标准的双重检查加锁，并用 8 线程并发验证：零失败，两个模型各只有一个实例。

**4. 提示词约束的失衡** —— 从幻觉滑到过度拒答

原提示词写的是「**尽量**基于参考内容作答」。「尽量」二字给了模型退路：
问「小米路由器怎么设置」时，它先正确说明手册中没有，接着基于自身知识补了一整套
小米路由器 App 的操作步骤。知识库问答的底线是只基于检索内容作答，
越过这条线用户就无法分辨哪句有出处、哪句是模型编的。

改成硬约束后却滑向另一个极端：问「H3C 路由器缺省密码都是 admin 吗」，
明明三台设备的手册都白纸黑字写着 admin，它却答「手册中未涉及」——
因为问法是疑问句、原文是陈述句，它便认定"没有直接对应的信息"。

最终的平衡点是显式列举哪些情况**必须作答**：答案分散在多片段需要归纳、
问法与原文措辞不同但说的是同一件事、只有部分信息可用（此时给出已有部分并点明
局限）。只有确实找不到任何依据时才说明未涉及。

**5. 评测器的判定顺序错误** —— 把「先拒后答」误判为纯拒答

判定顺序原本是先判拒答、再比关键词。而「手册中未提供实测数据，仅说明标称速率为
1200 Mbps，该数值为理论最大值」这种回答，开头命中拒答特征词，实质上却给出了
该给的信息——关键词比对根本没机会执行。「先说明没有 X，再给出相关的 Y」
是一种正确且常见的回答模式，修正为答案命中任何关键事实时不按拒答处理。

**6. 模型推理的并发竞态** —— 与第 3 条同源，但在另一个层面

第 3 条给单例加锁只解决了「模型被加载一次」，多个线程仍会**并发调用同一个
模型实例**。在 GPU + FP16 下这会抛 `expected scalar type Half but found Float`：
半精度推理过程中存在临时的 dtype 转换，两个线程的中间态互相污染。

CPU + FP32 时类型宽容得多，同样的代码完全不报错——所以这个缺陷要等到
**同时满足「GPU」「FP16」「并发」三个条件**才会暴露，切换推理设备时才浮现。

症状也具有迷惑性：整套评测准确率 96% → 28%，但检索、融合、精排各环节的日志
全都正常，召回条数、保留条数一条不少。唯一的线索是一条被淹没的
`精排失败：expected scalar type`，以及「单并发正常、双并发崩溃」这个对照。

修复方式是把推理调用也串行化，并与初始化锁分开——初始化只发生一次，
推理每次调用都要走，共用一把锁会让首次加载期间的等待语义变得含糊。
代价很小：GPU 上单次编码约 100ms，而链路中的 LLM 调用本就是秒级，
推理并非吞吐瓶颈。8 线程 × 3 轮并发压测零失败。

### 已知问题

**L1-04：附录章节召回失败**（唯一未通过项）

问「NR-1200W 怎么恢复缺省登录密码」，手册的标准答案是「通电状态下用针状物按住
Reset 键 5 秒，直至诊断指示灯慢速闪烁」，这段内容位于手册的「附录 - 故障排除」
章节，检索未能召回。模型转而给出了 `admin acl default` 命令——那恢复的是 IP
访问权限而非登录密码，答非所问。

这是真实的检索缺陷而非评测口径问题，**刻意保留为失败项**：把它调过去只需要放宽
关键词，但那样就掩盖了一个真实存在的召回短板。

**跨设备归纳与单设备过滤的结构性冲突**

问「H3C 的路由器缺省密码都是 admin 吗」这类针对一类设备而非某一台的问题时，
商品名归一化会把检索范围锁到单台设备上，可能恰好锁到手册里没写该信息的那台。
当前靠提示词层面的归纳要求缓解，根治需要让问题理解节点能识别出
「问的是一类设备」并跳过过滤。改动较深，列入 Roadmap。

## 后续演进方向

**父子块检索。** 召回时匹配小块保证精度，送入模型前回查父块补全上下文——
兼顾「检索要精准」和「生成要完整」这对天然矛盾。

**图谱检索接入。** `node_query_kg` 已在任务映射中预留位置，接入 Neo4j 后可以回答
「A 和 B 有什么区别」这类需要跨文档关系推理的问题，纯向量召回对此无能为力。

**消融实验。** 分别关闭 HyDE、稀疏向量、精排三个组件，量化各自的实际增益,
为后续取舍提供依据而不是凭直觉保留全部组件。

**流式输出。** 答案生成改为流式返回，把用户感知延迟从「等完整答案」缩短到「等第一个字」。
